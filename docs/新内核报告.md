# 新内核进展报告（2026-10-25）

对象：把站内 C++ 编译内核从 **runno / binji clang 8.0.1** 换成 **自研 LLVM 23.1.0 + wasi-sdk 34（`wasip1` + `eh`）**。

一句话状态：**内核编出来并跑通了，阶段 1 的精简 sysroot 已打包验完，阶段 2 的前端接线与阶段 4 的自写 WASI 宿主都已在 dev 跑通**（`runnoSandbox.js` 已切 `23.1.0`，`verify:judge` 20/20；首编从 13–17 s 回到 0.5–1.2 s）。后台预取与客户端单档清理已在本地 preview 验过；阶段 6 的浏览器能力探测 + 闸门也已落地（2026-10-25），用户可见文案（两版 guide / `help.js` / 使用手册 / NOTICE / noscript）与性能表同一天按 23 档重写，生产未发。语言档位、Runner、编译旗标、体积预算、探测与回退口径都已拍板（§3.1），只剩第 5 项空指针方案待定。

本报告的数字分三类，读到就按类别理解：
- **实测**：本机或线上真实跑出来的，标明口径；
- **外推**：由实测按比例推的，标明依据；
- **未测**：还没有任何数据的，明确写「未测」。

### 1.1 三个必须先看清的事实

1. **传输涨 ~1.3–1.9 倍，常驻回到同量级。** 预压 br 后首访 23.23 MiB（现役 17.75）；若只能吃 Vercel 的压缩档位则是 ~32–33。精简后 sysroot 解包 11.67 MiB / 1385 条（旧 9.49 / 416），整份常驻外推 **~+27 MiB**（重裁前那份 28 MiB 的估法是 +90）。阶段 4 仍要改挂载方式，但已不是「不可接受」。
2. **`-Oz` 不是体积的解，`--strip-all` 才是。** 剥 name/debug 段让内核从 166.17 → 115.20 MiB（br11 21.69），几乎等于 `-Oz` 的效果，却**不付编译速度**；`-Oz` 会让编译慢 **1.69×**（本机交替 6 轮复测：984 → 1732 ms）。
3. **能力是真涨了。** 旧内核没有异常、只有 C++17；新内核 `try/catch` 与 C++20 库都已实测能编、能链、能跑。代价是 PCH 变大（c++20 17.54 MiB，是旧 8.61 的 2.0×）和判据要跟着改。

### 1.2 为什么 runno 那个包明显小

| 段 | 旧 clang.wasm | 新 clang.wasm（原样） |
|---|---|---|
| code | 24.01 MiB | 66.80 MiB |
| data | 5.56 | 6.69 |
| name | ~0 | 26.38 |
| debug | ~0 | 3.50 |

1. **主因是 LLVM 8 → 23。** 只算 code 段，clang **2.78×**、lld **2.69×**。15 个版本的前端、后端、诊断都在长；旧包没有 C++20 库、没有异常 —— 能力差距就是这部分体积。
2. **次因是旧包本来就没 name / debug 段。** 新包原样 166.17 MiB 里，name 43.98 + debug 6.98 = **50.96 MiB**；默认 `--strip-all` 后是 115.20 MiB。旧包 48.36 MiB 里几乎没有这类内容。这部分已经免费拿到了。
3. **sysroot 已回到同档。** 旧 1.71 MiB / 9.49 MiB / 416 条，新 1.54（br）/ 11.67 / 1385。条目多是因为 libc++ 20 把实现头拆细了（旧 libc++ 8 是 196 个扁平头），字节数只多 2 MiB。

结论：**「小」买的是「旧」**。要 C++20 + 异常，code 段这 2.7× 躲不掉；能免费拿的 50.96 MiB 已经拿了。

## 2. 已经做了什么

### 2.1 前置：把旧方案固化成绝对基准

`HANDOFF.md` §18（2026-10-24 建）把现役 runno 方案量成了可复测的基准：网络传输逐件、内存三个口径、加载 / 编译 / 运行分段、stdin/stdout scaling、线上首访三次实测、Python 那条线。**之后所有改进都与它比**；复测方法在 §18.8。

### 2.2 阶段 0：两颗内核编出来并跑通

- 产物：`tools/wasm-core/out/23.1.0/{clang.wasm, wasm-ld.wasm}`（`tools/` 在 `.gitignore`，**不进仓库**）。
- 一字命令复跑：`node scripts/wasm-core/build.mjs`（增量）；`--opt` 额外跑 `wasm-opt -Oz` 体积探针。
- 构建面：`fetch.mjs`（下载 + sha256 + 解压）、`versions.json`（版本只钉这一处）、`build.mjs`（原生 tblgen → wasm clang + lld 两段式）、`toolchain-wasip1.cmake`、`compat-include/`。

移植上只改了 LLVM 三处源码（全部幂等，未命中会告警）：

1. `Unix/Program.inc`：`ru_maxrss` 按 `__wasi__` 排除（wasi 的 `struct rusage` 只有两个字段）；
2. `llvm/include/llvm/Support/Compiler.h` 与 `clang/include/clang/Support/Compiler.h`：上游 wasm 分支写的是大写 `__WASM__`，clang 定义的是小写 `__wasm__`；不改则 `CLANG_ABI` 未定义，`Attrs.inc` 整片崩掉（44 个失败点里的绝大多数）。

兼容面：`signal.h`（`SA_*` / `siginfo_t` / `kill`）、`sys/wait.h`（`wait4` / `WNOHANG`）、`unistd.h`（必须先拉 `sys/types.h`，否则 CMake 的符号探测全错）、`fchown`；外加一个真符号 `posix_madvise`（wasi-libc 只有声明）。

工具链文件里四个坑（都已在文档里定死）：`*_FLAGS_INIT` 只播种缓存要用 `CACHE ... FORCE`；wasm-ld 默认栈仅 64 KiB，要显式给 8 MiB；`-lpthreads` 是 `STATIC_LIBRARY` 探测造成的假阳性（`-DHAVE_LIBPTHREAD=OFF`）；补 `_WASI_EMULATED_GETPID`。

### 2.3 验证口径（运行时接线要照抄的）

- **cc1 直调**（站内走的就是这条路）：`-fexceptions -fcxx-exceptions -exception-model=wasm -target-feature +exception-handling -mllvm -wasm-enable-eh`，六项缺一不可；缺 `-target-feature +exception-handling` 会在后端崩。
- 必须带 `-resource-dir <sdk>/lib/clang/23`（否则 `stddef.h file not found`）。
- 链接：`wasm-ld.wasm -flavor wasm`（argv[0] 不是 wasm-ld 就必须显式）；要 `lib/wasm32-wasip1/crt1-command.o`（否则 `_start` 未定义）、`-L …/lib/wasm32-wasip1/eh -lunwind`、`-L <sdk>/lib/clang/23/lib/wasm32-unknown-wasip1 -lclang_rt.builtins`（否则 `__multi3` 未定义）。
- 产物在 Node `node:wasi` 里跑出 `before / caught: vector / len=5`。

### 2.5 阶段 1：sysroot 取子集并打包（已完成）

- 验证（C++20 + 异常，从最终 **br 包**解压后跑）：站内 29 个万能头 + `<format>/<ranges>/<span>/<numbers>`、`regex/filesystem/fstream/random/complex/chrono/valarray/locale`、`throw/catch`、`__int128`、`%Lf`、PCH（带 PCH 与不带 PCH 的 `.o` 逐字节一致）。

### 3.3 阶段 2：前端接线（dev 已通，编译性能待阶段 4）

**已落地（2026-10-25）**：
- 三件 `.br` 资产进 `public/wasm/23.1.0/`；`runnoSandbox.js` 的版本、URL、头路径、cc1 / 链接参数全换；`PCH_CACHE_VERSION` 5（阶段 4 又因 PCH mtime 修正升到 6）；`compileCache` 加 `toolchain` 键；`native.rs` 升 `c++20`。
- `vite.config.js` 的 dev / preview 中间件与 `vercel.json` 都补了 `Content-Encoding: br` + 正确 MIME；本地 dev / preview 实测头正确，**Vercel preview 上的实际效果仍未验**。
- **新标准 exnref**：libc++ 的 `try_table`/`throw_ref` 与 legacy 混用会被 V8 拒绝，用户代码必须走 `-wasm-use-legacy-eh=false` + `+multivalue` / `+reference-types`；`-triple wasm32-unknown-wasip1` 必给。
- **runno 的缺文件 errno**：`path_open` / `pathStat` 返回 `ENOTCAPABLE` 会让 clang 23 的 `__has_include(<features.h>)` 直接 fatal；`patch-wasi-clock.mjs` 已补 `ENOENT`。
- 验收：`npm run verify:judge` **20/20 PASS**；PCH 18.37 MB；SIMD / `throw` / `<format>` 都过；2M 排序自报「已排序 14–36 ms / 随机 100–135 ms」。
- **阶段 2 的缺口已被阶段 4 收回**：首编从现在起 **855–1234 ms**、之后 502–608 ms（阶段 2 当时是 13–17 s）。双档探测 / 回退仍未接。

原接线清单（留作对照）：

路径与参数要逐条换：`/sys/include/c++/v1` → `/sys/include/wasm32-wasip1/eh/c++/v1`；`/sys/include` → `/sys/include/wasm32-wasip1`（**不要**再加 `/sys/include`，新布局顶层没有通用头层）；`/sys/lib/clang/8.0.1/include` → `/sys/lib/clang/23/include`；`-L` 加 `eh`；`crt1.o` → `crt1-command.o`；builtins 改名；追加 `-lunwind`；`-fwasm-exceptions` 进 `FRONTEND_ARGS`；万能头落点改 `/sys/include/wasm32-wasip1/bits/stdc++.h`。

已经踩到、接线时必须处理的：
- **clang 23 的 cc1 删掉了 `-fmessage-length`**，站内 `FRONTEND_ARGS` 里有这一条，会直接 `unknown argument`；**`--no-threads` 也不再被 LLVM 23 的 wasm-ld 接受**，链接行里要删；
- `-std=c++20`（已定）要同时改沙箱与桌面壳 `native.rs`（跨端契约）；注意 clang 8 只认 `-std=c++2a`，**不能提前改现役 `runnoSandbox.js`**；
- **拍板新增两条参数**：cc1 写 `-target-feature +simd128` + `-fno-rtti`（**不是** `-msimd128`，cc1 会报 unknown argument）；两条都属于语言选项、一起进 PCH 签名；`dynamic_cast` / `typeid` 从此变 CE，guide / 使用手册要写明；浏览器下限由**新标准 EH**决定（Chrome 137+ / Firefox 131+ / Safari 18.4+），不是 SIMD 的 Safari 16.4；
- PCH 签名变化 → `PCH_CACHE_VERSION` 必须 +1，`compileCache` 键要加内核版本；
- 语法诊断（`syntaxDiagnostics.js`）走同一颗 `clang.wasm`，参数也要同步；
- **分发格式要跟着换**：三件资产改成预压 `.br`（`clang.wasm.br`、`wasm-ld.wasm.br`、`sys23-fs.tar.br`），响应必须带 `Content-Encoding: br` 才会被浏览器透明解开。`DecompressionStream` 不能当兜底（Chrome 155 不认 brotli）；dev 下由 vite 中间件补头，线上由 `vercel.json` 的 `headers` 补，**这条要在 preview 部署上实测 HIT/MISS**（Vercel 若改写/压缩它，前端会拿到压缩字节，症状是 wasm 解析立刻失败，很好认）；
- **`cp-toolchain` 的配额要重新算**：Cache Storage 存解码后字节（实测 1.54 MiB br 落桶 15.6 MB），新工具链稳定态 **~131 MiB**（旧 48–50 MiB）。

## 4. 风险与口径提醒

1. **线上 ~32–33 MiB 是外推，不是实测。** 依据是 §18.1 的线上 br 比本机 br11 弱约 1.31×；换 CDN / 缓存策略就失效。
2. **本机 Node 的编译时间不能当浏览器数。** §19.7 的 825–908 ms 含进程启动与 100 MiB 模块实例化，和 §18.3 的浏览器口径不是一回事，只能比相对值。
3. **~+27 MiB 常驻也只是外推**（按 §18.2 的「内容 8.4 MiB → 页面 +19.28 MiB」比例）。要在阶段 4 用 `measureUserAgentSpecificMemory` 实测。
4. **能力矩阵已有红绿表**（`HANDOFF.md` §19.9 / §19.10，能力组 13/13、判定组 23/23）；仍缺的是 wasm vs native 倍率表与浏览器里的真机实测。
5. **异常一开，判据就会动。** 旧的 `abort → 134 → MLE` 是基于 `-fno-exceptions` 的行为；`std::bad_alloc` 被用户 `catch` 之后的归属已经在 `docs/评测判定规范.md` §5.2 / §9 #22–#23 按权威口径重写（2026-10-25），不要只留在代码注释里。
6. **工作树里所有这些改动都未提交**（含基线所需的时钟补丁）。要提交时按主题拆，别把工具链产物带进仓库（`tools/` 已忽略）。
