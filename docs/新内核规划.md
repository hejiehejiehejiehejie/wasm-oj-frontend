### 2.2 「重编 sysroot 开异常」的六步操作

**整段六步里，步骤 1–5 全部作废 —— 不是做法错，是前提过期了。** wasi-sdk 从 28 起，预编译包里就**并存两支 libc++**，现场已核（`tools/wasm-core/.cache/wasi-sdk-34.0-arm64-macos/share/wasi-sysroot/`）：

```
include/wasm32-wasip1/eh/c++/v1      16 MiB   ← 开了异常与 C++17 以上
include/wasm32-wasip1/noeh/c++/v1    16 MiB   ← 关异常那一支（本次不取）
lib/wasm32-wasip1/eh/libc++.a     9,042,484 B ; libc++abi.a 1,440,040 ; libunwind.a 13,594
libc-printscan-long-double.a        112,154 B   ← §7 那颗 long double 补丁需要的库，上游已带
```

> **站内现在吃的正是 `noeh` 那一支的等价物**：`__config` 里自带 `_LIBCPP_CXX03_LANG`，于是 `try`/`throw`、`std::regex`、`to_chars`/`from_chars`、`std::complex`、`random_device`、`filesystem::current_path` **全是编译错误**（`HANDOFF.md:820`，23 段程序实测）。所以「开异常」这件事的真实工作是**换打包时取哪一支目录**，不是重编 LLVM。

### 2.3 裁剪 LLVM 产物与 sysroot

| 建议 | 裁决 | 依据 |

| `LLVM_TARGETS_TO_BUILD="WebAssembly"`、只留 clang、禁 ObjC | ✅ | 全在 `build.mjs`，而且做得更多：`FEATURE_OFF` 关掉 zlib/zstd/libxml2/terminfo/libedit/curl、测试与 benchmarks；`LLVM_ENABLE_EH=OFF`、`RTTI=OFF`、`THREADS=OFF`；`CLANG_ENABLE_STATIC_ANALYZER=OFF`；`lto`/`libclang` 两个 SHARED 目标不建（wasm 无动态链接，配置期就报错） |

### 2.4 判定（用户已定稿在 `docs/评测判定规范.md`）

本文**不重开判定语义**。只标外部建议与规范/实测的三处冲突，免得照抄进实现：

| 外部建议 | 裁决 | 依据 |
| --- | --- | --- |
| TLE 必须把 wasm 放进 Web Worker、主线程 `setTimeout` 到点 `terminate()` | ✅ 已如此 | 见 §2.1 最后一行。规范里这条的待办不是「加 worker」，是**把「到点即杀」改成 `T + max(100 ms, 5 %)` 再看程序结束时刻**（`评测判定规范.md` §4.2） |
| 「传 `--no-check-features` 或用链接脚本保留/废弃第 0 页」来拿到空指针 RE | ❌ **两处硬错** | `wasm-ld --help` 实测：`--no-check-features` 是「Ignore feature compatibility of linked objects」，与第 0 页毫无关系；而 lld 的默认就是 `--stack-first`（"Place stack at start of linear memory (default)"）——栈就在线性内存最前，所以**没有任何开关能让 `*nullptr = 1` trap**。站内实测吻合：偏移 0 可读、不 trap → 读垃圾值正常退出判 WA（`HANDOFF.md:818`）。剩下的只有两条：`-fsanitize=null`（每次访存加检查，代价直接打在性能倍率上）或接受现状并把它记成已知偏差 → §5 第 5 项 |
| MLE 用「写死 `maximum` 一刀切」就极其精确 | ❌ 与实测冲突（换内核后按规范的证据链收口） | §18.2 实测：`--max-memory=64MiB` 下程序想 `new` 400×1 MiB 只成功 **62 次、exit 0、8 ms** —— 分配失败既不 trap 也不抛。现行 MLE 判据「开上限 + 退出码 134 + stderr 全空」是启发式，所以 `abort()` 会被误判 MLE（规范 §10 的 P0-2）。**已定（用户 2026-10-25）：按 `评测判定规范.md` / 权威测评机口径执行，不新造判据** —— `new` 失败未捕获 → terminate → 134 + `sbrkFailures > 0` → `MLE`；被 `catch` 后正常退出 → 按程序自身结果判。规范 §5.2 / §9 #22–#23 已按此改写，新内核实测通过 |
| UB / 越界在 wasm 与 Linux 下表现一致（都是随缘 WA） | ✅ | `HANDOFF.md:818` 同结论 |

### 2.5 减小倍率 / 接近原生

| 建议 | 裁决 | 依据 |
| --- | --- | --- |
| 开 `-msimd128` | ✅ **已定：开（用户 2026-10-25 拍板）** | 三条前提照做：① 它是语言选项 → 进 PCH 签名；② **编译与链接的 target features 必须一致**（实测：cc1 不认驱动层 `-msimd128`，要写 `-target-feature +simd128`；链接侧不用额外旗标，lld 按对象带入，`wasm_simd128.h` 用例已跑通）；③ **浏览器下限上修到 Safari 16.4**（SIMD 在 15.2 没有），双档探测要把「有 SIMD」当成新档准入条件。收益挂 §6 倍率表验收 |
| `-O2` 升 `-O3` | ❌ **已定：不升，保持 `-O2`（用户 2026-10-25 拍板）** | `-O2` 是与 CF/AtCoder/USACO 对齐过的**规范性下限**（`评测判定规范.md` §6「不得低于 -O2」），升 `-O3` 是偏离行业口径换性能。用户口径：这是高频「点一下运行」的 Web IDE，**编译速度优先于产物性能与体积**；`-O2` 已能给出接近原生的运行期，同时把编译压得足够便宜（老机器也扛得住）。不做 §2.5 那条三档倍率对照里的 `-O3` 档 |

| 预分配满额静态内存 `new WebAssembly.Memory({initial:4096,maximum:4096})` 消灭 `memory.grow` | ❌ **实测说它不贵，而且有害** | §18.4：160 MB alloc+memset 那一次**自报 14 ms、运行段 22 ms** —— 一路 grow 到 161 MiB 全程只花这点钱，不是「隐形灾难」。反过来把 initial 顶到上限，每一次运行（含 hello world）都先承诺 256 MiB 页，还会顶破规范 §5.2 那条「`--max-memory` 含栈含堆的总上限」语义。附带纠正：wasm 线性内存 grow **不会**把 ArrayBuffer detach 掉用户代码的指针（只有 JS 侧持有的 view 会失效，而 stdin 槽是 SAB，不参与 grow） |

| 「6.7 倍倍率的元凶是强制边界检查」 | ⚪ **这个数站内没复现过** | 已知的是绝对值：2M 排序自报 30–32 ms、运行段 37–41 ms（§18.3/18.4）。**本机 native 对照从没量过**，所以 6.7× 不能当基线。阶段 3 要补一条倍率表：`-O2` / `-msimd128` 两档 × 2M 排序 + 384³ 矩阵乘 + 160 MB memset，对照走**现成的 `native` 引擎**（桌面壳那条 `run_cpp_core`，`HANDOFF.md:1808` 起）。SIMD 的收益挂这张表验收，不挂外部那张图（`-O3` 已定不开，见 §5 第 4 项） |

### 阶段 1 —— sysroot 取子集并打包（**已完成 2026-10-25**）

- **产物**：`scripts/wasm-core/pack-sysroot.mjs`（`npm run wasm:core:pack`）→ `out/23.1.0/sys23-fs.tar.br`（同一条命令顺手产出 `clang.wasm.br` / `wasm-ld.wasm.br`），条目以 `sys/` 开头。
- **最终规格（实测）**：tar.br **1.54 MiB**（同一份 tar 的 gz9 是 2.23），解包 **11.67 MiB / 1385 条**。对比现役 `clang-fs.tar.gz`：1.71 MiB / 9.49 MiB / 416 条 —— 解包体积基本回到同一档；条目多是 libc++ 20 把实现头拆细了（旧 libc++ 8 是 196 个扁平头）。
- **为什么用 br 而不是 gz**：Vercel 给现役 clang 的 br 比本机 q11 差 ~1.38×（§19.8），所以我们自己压到 q11 并用 `Content-Encoding: br` 直接发；客户端拿到的就是解好的 tar。`DecompressionStream` 不能兜底（Chrome 155 只认 gzip/deflate）。
- **裁掉的东西**：
  - 头：四个 target 只留 `wasm32-wasip1`；libc++ 只留 `eh` 一支，丢 `noeh`、`__cxx03`（C++03 冻结副本，只在 `__cplusplus < 201103L` 时被 include）、`eh/mach-o`、模块图；`experimental-coop-threads` 整棵不取；
  - clang 内置头：8.27 MiB → **316 KiB**。只留 C/C++ 语言头（`stdarg/stddef/stdint/float/limits/…`）与 `wasm_simd128.h`，丢掉 x86/arm/riscv/hexagon/CUDA/HIP/OpenCL 的 intrinsic 头；
  - 库：丢全部 `.so`、`llvm-lto/`、`libc++experimental.a`、`libc-printscan-no-floating-point.a`；保留 `crt1-command.o`、`libc.a`、`libc-printscan-long-double.a`（`%Lf` 要用）、`libsetjmp.a`、各 8 字节空归档（`-lm` 等要能链过）、`libwasi-emulated-*`，以及 `eh/{libc++.a,libc++abi.a,libunwind.a}`；
  - 归档内 `.a`/`.o` 一律 `llvm-strip --strip-debug`（**不能** `--strip-all`：链接器还要符号表）。
- **builtins 落点**：`/sys/lib/clang/23/lib/wasm32-unknown-wasip1/libclang_rt.builtins.a`（名字少了 `-wasm32`）；clang 内置头落 `/sys/lib/clang/23/include`。
- **万能头**：不进包，继续由站点运行时注入，但路径要跟着新布局走 —— **`/sys/include/wasm32-wasip1/bits/stdc++.h`**（旧的 `/sys/include/bits/stdc++.h` 作废）。
- **验过**（C++20 + 异常，最终 tar 解包后跑的单文件程序）：站内 29 个头全量 + `<format>`/`<ranges>`/`<span>`/`<numbers>`；`regex`/`filesystem`/`fstream`/`random`/`complex`/`chrono`/`valarray`/`locale`；`throw/catch`；`__int128`；`printf("%Lf")`；PCH 生成 + 带 PCH 编译（`.o` 与不带 PCH **逐字节一致**）。
- **头清单比对**：旧包有、新包没有的只剩 clang 8 的 libc++ 内部头（`__debug`、`__errc`、`__threading_support`…）与 runno 自带的 `canvas.h`/`libintl.h`；公开头全部在（`stdarg.h`/`stddef.h` 由 clang 内置头提供）。
- **一处旧判断作废**：这份 sysroot 的 `include/` 顶层没有「通用头层」，只有 `c++/`（空）和四个 target 目录；`-internal-isystem /sys/include` 不必再加。

  | 2M 随机排序自报 / 运行段 | 28–34 / 37–41 ms | **36–40 / 37–43 ms** |
  | stdin 1 MiB / 4 MiB 墙钟（命中编译缓存） | 1 MiB ≈ 643 ms | **2–4 ms / 5–8 ms** |
  | 5 MB 输出宿主收口 | 270–360 ms | **62–80 ms**（`runMs` 22–29 ms） |
  | `verify:judge` | 20/20 | **20/20 PASS** |

- **两个宿主侧的坑（都已修）**：
  1. **目录的 `rights_inheriting` 必须带文件权限**。wasi-libc 的 `open()` 拿目录的 inheriting 拼 `path_open` 的 rights_base；只给 `DIR_RIGHTS` 时 clang 写 `.o` 会 `EBADF`（`unable to open output file '/program.o'`）。`host.js` 已改成 `DIR_RIGHTS | FILE_RIGHTS`。
  2. **PCH 源头的 mtime 必须固定**。`MemoryFs` 默认用 `Date.now()`，PCH 生成与加载两次写入 `/stdc++.h` 的 mtime 不同，会报 `/stdc++.h has been modified since the precompiled header was built`。worker 用常量 `1_700_000_000_000`，`PCH_CACHE_VERSION` 升到 6。
  3. 自写宿主的 fd 2 是 CHARACTER_DEVICE，clang 23 会默认开彩色诊断；`FRONTEND_ARGS` 显式加 `-fno-color-diagnostics`。
- **未做**：生产部署真跑（build 已出 `wasi.worker-*.js`，但没在 Vercel preview 上点过）；**启动探测已接**（2026-10-25，见阶段 6）；用户可见文案（两版 guide / `help.js` / 使用手册 / NOTICE 第二节 / noscript）已于 2026-10-25 全部改成 clang 23 + C++20。

- **要什么**：stdin ≥ 20 MB/s（基线 1.6）、5 MB 输出的宿主收口 ≤ 80 ms（基线 270–360）、**首编回到 505–715 ms 量级**（阶段 2 实测 13–17 s，根因是 runno 每次 run 重新实例化 + 整份 sysroot structured clone）。sysroot 常驻原来写的「≤ +10 MiB」**已作废**：精简后内容 11.67 MiB / 1385 条，按 §18.2 比例外推 ~+27 MiB，所以验收改成「不再整份常驻 / 不按消息整份复制」，绝对值进阶段 4 实测。
- **为什么 B 就能到底**（三条都不是「优化」，是把黑盒换成自己的代码）：
  1. **stdin**：`fd_read` 由我们实现，每次调用从 JS 的 `Uint8Array` 同步拷进 guest 内存（iov 多大拷多大），没有 runno 那个「每 8 KiB 一个 `setTimeout(0)`」的 tick。1.6 MB/s 的锅在轮询，不在块大小 —— 不再需要「先把输入整段预置进内存」这条更激进的写法，**普通 `fd_read` 即可达标**；
  2. **stdout**：`fd_write` 攒块，运行结束一次 `TextDecoder` 解码，不发生逐块跨线程 postMessage；
  3. **sysroot**：worker 里只 untar 一次、Map 常驻，不再每次运行 `{...tool.sysroot}` 整份 structured clone（`runnoSandbox.js:504`/`:936`）。
  顺带：`clock_time_get` 直接按 `performance.now()` 实现，C++ 侧不再依赖 `patch-wasi-clock.mjs`。
- **施工顺序（每步都要有可复核的证据）**：
  1. **取实际 import 表（已完成，2026-10-25 实测）**：`WebAssembly.Module.imports()` 扫本机资产 ——
     | 模块 | import 模块名 | 条数 |
     | --- | --- | --- |
     | 现役 `public/wasm/8.0.1/clang.wasm` | `wasi_unstable` | 27（含 `poll_oneoff`） |

     **两条不能漏的结论**：① import 模块名从 `wasi_unstable` 变成 `wasi_snapshot_preview1`（宿主按「同一张函数表、两个模块名」注册，别只认一个）；② 样本里没出现不代表用户代码不会带出新调用（`fstream`、`readdir` 一类会拉进 `fd_advise`/`fd_readdir`），所以宿主必须**按上表全量实现并给未实现调用一个可诊断的 trap**，不能只写样本那 6 个。两代编译器都导出 `memory` + `_start`（新内核不再导出 `__heap_base`），宿主取内存走 `instance.exports.memory`；

## 5. 拍板记录（8 条；第 1 / 2 / 3 / 4 / 6 / 7 / 8 已定，只剩第 5 待定 —— 动手前问用户）

1. **Runner 三选一 —— 已定：B（C++ 自写宿主、Python 留 runno，用户 2026-10-25 拍板）**。理由：I/O 那条要到底（`fd_read`/`fd_write` 自己实现、`Memory` 自己持有）就必须拿回宿主，而 Python 那条线现在没有任何问题要修，重写它只增风险。落地口径：
   - **C++ 全链路（cc1 编译、link、运行、`-fsyntax-only` 诊断）都走新宿主**，`@runno/wasi` 只留给 Python。所以短期内确实是双内核并存，但**分界线是语言，不是功能**；
   - 新宿主从 `WebAssembly.Module.imports()` 实测出的调用表出发（不照抄「约 15 个」的估计），旧 runno 路径在验收通过前保留为回退档；
   - `scripts/patch-wasi-clock.mjs` 对 C++ 侧随宿主一起退场，**对 Python 侧仍要保留**（`node_modules` 那颗补丁不能删）；
   - 工作量与出口判据见阶段 4。
2. **C++ 标准 —— 已定：`c++20`（用户 2026-10-25 拍板）**。依据（`HANDOFF.md` §19.7/§19.8）：三档下载体积完全相同；用户产物体积也一致；差别只在 PCH —— 17/20/23 = 14.38 / 17.75 / 20.67 MiB（按精简包 `/sys` 路径重测 c++20 是 **17.54 MiB**），PCH 落在 IndexedDB 直接吃配额，17→23 还会让 PCH 建得慢 52%。c++20 已覆盖竞赛常用库（范围/`span`/`format`/`numbers` 均已实测），23 独有库没有再买的必要。升档要同步桌面壳 `native.rs` 与两版 guide。
3. **异常开了之后 MLE / RE 判据 —— 已定：按 `评测判定规范.md` / 权威测评机口径执行（用户 2026-10-25 拍板）**。落地口径：MLE 的唯一判据仍是「内存上限直接导致终止」——
   - `std::bad_alloc` **未捕获** → terminate → abort（134），且 `sbrkFailures > 0` → `MLE`；
   - 被用户 **`catch` 后正常退出** → 按程序自身结果判（同 `malloc` 返回 NULL 后 AC，§9 #18），不因「曾经分配失败」判 MLE；
   - 不新造判据、不把 `bad_alloc` 一律折成 `RE`、不上 `-fsanitize=null` 兜空指针。
   规范 §5.2 / §9 #5 / #22–#24 已按此改写；`verify.mjs` 实测 #22 = MLE、#23 = AC、#24 = CE（`dynamic_cast` 的 `-fno-rtti` 代价）。
4. **四颗编译旗标 —— 全部已定**：
   - **`-O3`：不开，保持 `-O2`（用户 2026-10-25 拍板）**。理由见 §2.5：编译速度优先于产物性能，`-O2` 与 CF/AtCoder 同档且是老机器能承受的编译开销。
   - **`-flto`：不默认，参数里也不加（用户 2026-10-25 拍板）**。产物在浏览器 VFS 里、不传输，体积无关紧要；LTO 会把编译时间加到每一次首编上。仓库现状已经没有任何 `-flto`，保持即可。
   - **`-msimd128`：开（用户 2026-10-25 拍板）**。cc1 必须写 `-target-feature +simd128`（驱动旗标 `-msimd128` 在 cc1 里是 `unknown argument`，实测）；链接侧不加旗标、由对象带入；`wasm_simd128.h` 用例已跑通；进 PCH 签名；**单看 SIMD 是 Safari 16.4，但整体下限由新标准 EH 决定（Chrome 137+ / Firefox 131+ / Safari 18.4+）**。
   - **`-fno-rtti`：开（用户 2026-10-25 拍板）**。进 PCH 签名；`dynamic_cast` / `typeid` 从可用变 CE，两版 guide / 使用手册 / 规范 §8 要写明；桌面端是否同步禁 RTTI，阶段 6 一并定（否则同一份代码跨端分叉）。
5. **空指针 RE（仍待定；候选方案已实测）**：接受「读 0 不 trap → WA」这个 wasm 固有偏差，还是上 `-fsanitize=null`（每次访存加检查，性能倍率立刻可见）。当前规范按「记成已知偏差、不上 sanitizer」写（§5.2），但没有单独拍板。**2026-10-25 实测候选方案（`-fsanitize=null -fsanitize-trap=null` + 可选 `nonnull-attribute`）**：
   - **可行性**：这对参数能编、能链、**不需要任何 UBSan 运行时**；只写 `-fsanitize=null`（不带 trap）会在链接期缺 `__ubsan_handle_type_mismatch_v1_abort`，必须成对使用。
   - **覆盖**：对「运行时零指针」（`volatile` 0，编译器不知道是 0）的**读、写、成员访问**三类都 `unreachable` trap → `RE`；**`memset/memcpy(nullptr)` 不 trap**，加 `-fsanitize=nonnull-attribute`（trap 侧同名）才 trap。代价：`memcpy(v.data(), src, 0)` 这类 n=0 的 UB 也会判 RE（可接受，但要写进已知偏差）。预编译 libc++ 内部与变参指针仍不覆盖。
   - **开销**（长基准、交替 A/B、成对中位数，9–16 轮）：sort **~0%**、链表 **~0–1%**、BST / `std::set` **~0–2%**、`std::map` **~0–3%**、SIMD 循环 **~0–3%**、384³ 矩阵乘 **~1.5–2.5%**；单次长序列曾出现 **+7%** 的离群值，重复测不复现（机器热降频 / 顺序噪声，不能当结论）。按 1 s 时限折算约 **+0–30 ms**。`.wasm` 体积**零增长**、编译时间在噪声内；全量 `wasm:core:verify` 带这组参数仍 **13/13 + 23/23**。⚠ 以上是 Node WASI 口径，浏览器 JIT 下要在阶段 2/3 复核一次。
   - **`--global-base=1024` 不可用**：默认 `--stack-first`，wasm-ld 直接报 `--global-base cannot be less than stack size when --stack-first is used`；默认布局下栈占 `0…stack_size`，全局数据在 **~64 MiB**，0 地址是栈底、不是 `.data`/环境变量。要用 1024 必须 `--no-stack-first`（改变整个内存布局，收益未测）。另外 `-Wl,` 是驱动写法，站内直调 cc1 / wasm-ld，不认。
   - **建议**：采 `-fsanitize=null,nonnull-attribute` + `-fsanitize-trap=null,nonnull-attribute`，弃 `--global-base`；接线时 PCH 签名与编译缓存键都要带这一档。
6. **体积与首访预算 —— 已定：接受；恢复后台预取；双档只留一份常驻（用户 2026-10-25 拍板）**。
   - **预算**：首访 **23.23 MiB**（本机 br11；线上若不认我们设的 `Content-Encoding` 则外推 ~32–33）与常驻 **~+27 MiB** 都接受；`-Oz` 仍不做。
   - **后台预取**：恢复。默认对 C++ 生效（`cp.autoPreload` 缺省视为含 `cpp`），等 SW `ready` 且页面已被 controller 接管、再等 idle 才动手（否则那几发 fetch 不进 `cp-toolchain`，§18.6 实测过）；Python / 题解渲染器仍按勾选。复用 `runtimePreload.js` 的串行队列，失败静默、不阻塞首屏。**预取只把三件资产下到 Cache Storage，不走 `preloadToolchain()`** —— 那条路会 `untar` 成 Map 常驻（~27 MiB），等于让每个访客都为没用到的语言付内存；首次点▶再解包 + 实例化。
   - **只留一套（硬约束）**：**仓库里仍放两份**（`8.0.1/` 是回退档，这是第 7 项的前提）；这里说的是**客户端存储**——稳态下 `cp-toolchain` 只存**当前档**。启动先定档（第 7 项），用当前档地址预取；**新档预取成功后才清旧档**（切换窗口内允许短暂并存，成功后立即清；Cache Storage 按 URL 逐个删、PCH 清掉旧版本、编译缓存里旧内核的产物按版本键清）；预取失败则保留旧档作为回退。这样 runno 兜底时不会和 23.1.0 并存。
   - **做不到的部分**：HTTP 缓存没有 JS 清除接口；SW 控制下以 Cache Storage 为准，HTTP 缓存里可能残留旧档字节直到浏览器自行淘汰 —— 要写进说明，不假装已清干净。
   - **指标口径**：预取不改变带宽，只把下载挪到用户看不见的地方。阶段 5 要分开量「后台预取完成时间」与「就绪后点▶的等待」，不能拿预取后的 0.6 s 冒充「首访 ≤ 8 s」。
7. **双档并存 —— 已定：做（用户 2026-10-25 拍板）**。`public/wasm/8.0.1/` 原样保留 + 新增 `public/wasm/23.1.0/`，启动时按探测结果**判定 23 档可用性**（探测物必须同时覆盖 wasm 异常与 SIMD；2026-10-25 追加：**不切档**，探测失败只给明确提示，见阶段 6）。代价（仓库里两份：旧 8.0.1 约 50 MiB + 新档裸 115.2 MiB、另加 sysroot tar 15.57 MiB）已接受；**客户端稳态只留一套**（第 6 项）。回滚 = **部署退回上一版**（`8.0.1/` 的资产只为这条路留着）。
8. **灰度范围与节奏 —— 已定：一次性换默认（用户 2026-10-25 拍板）**。`23.1.0` 直接成为默认；**不加 `wasm23` 自选档、不做两周灰度**。回退完全依赖第 7 项的双档并存（启动探测失败或线上出系统性问题时整档退回），不做出「两个引擎档并存」的开关。

## 7. 风险与「别信这些量法」

1. **UaMem 看不见 runno worker 里的 wasm 线性内存** —— 任何「省内存」的验收必须继续用程序自报 `sbrk(0)`，否则测不出收益也测不出回归（§18.2 第一条 ⚠，§18.7 第 5 条）。
2. **dev 的传输量与内存都不是线上口径** —— dev 实测 550 条 / 112.55 MiB、空载 108.51 MiB，线上是 3 条 / 1.21 MiB 与 23.13 MiB（差 4.7 倍，全是 monaco 未压缩 ESM 的账）。**但运行那条路上 dev 与线上一致**（§18.6：55–84 ms vs 57–63 ms），所以时间用 dev 量、体积与内存必须用线上量。
3. **`node_modules` 补丁的第二颗坑**：`@runno/wasi` 真跑用户程序的是 `dist/main.js` 里**内联的那份 worker 源码**，事后覆盖 prototype 无效；补丁必须连带删 `node_modules/.vite/deps`（Vite 预打包缓存键不含 node_modules 内容）。阶段 4 选 A 就再多背一颗这种补丁，选 B 才彻底摆脱（`HANDOFF.md:821`）。
4. **wasm 线性内存只增不减** —— 一次峰值会一路带到 worker 销毁，所以「常驻内存」的收益要靠**销毁重建**才量得出来；`unloadRuntime()` 的净残留实测 ≈0（§18.2），这条可以继续当验收工具。
5. **交叉编 LLVM 的时间与磁盘** —— `.cache` 已经 3.4 GB，wasm 段链接单 job（防 OOM），一次构建按小时计。**别在构建中途清 `tools/`**；`build.mjs` 走 ninja 增量。
6. **PCH / 编译缓存的版本钉子一旦漏改，症状是「改了参数但没变化」** —— 现象会像「新 sysroot 没生效」，实际是老存档被复用。三条钉子（`PCH_CACHE_VERSION`、`STACK_POLICY_VERSION`、`compileCache` 键）在阶段 2 一起动。
7. **换内核会把 `HANDOFF.md:820` 那张「已知编译错误清单」整张作废** —— 那张是 23 段程序实测出来的，新内核要重新跑一遍再删，不许推断。
8. 探针纪律照旧：一次性探针放 `/tmp`、只往 `localStorage` 播种、**不改仓库文件做测量**（`wasm-oj-browser-probe`）。
9. **`npm run build` 在这台机器必挂 safe-delete**（清 `dist/` 超 50 文件），要产物用 `npx vite build --outDir /tmp/…` —— 阶段 2/6 要验线上口径时一定会撞上。
10. **后台预取不改变带宽，只改变「谁在等」** —— 23 MiB 在 1.6–2.6 MiB/s 下仍是 9–15 s；预取完成后的点▶才是 0.6 s。验收必须把「预取完成 / 就绪后点▶ / 首访立刻点」三条分开，别合成一个数。
11. **「只留一套」只对 Cache Storage 有承诺** —— HTTP 缓存没有 JS 清除接口，旧档字节可能残留到浏览器自行淘汰；PCH 与 `compileCache` 能清，但要按版本键主动扫，不能指望 LRU。
12. **阶段 4 的 `kill()` 会 terminate 常驻 worker** —— TLE / 取消之后下一次 `loadToolchain` 要重新 init（untar 1385 条 + 编两个模块，约 0.4–0.7 s），所以别在 TLE 后立刻假设工具链还在；`runCpp` 已经按 `host.alive` 自动重建。

## 8. 明确不做 / 已被推翻的说法

- **不重编 wasi-sdk 的 sysroot**（`make package` 那一整段）：上游已带 `eh` / `noeh` 两支，换目录即可。
- **不手动删 `<thread>` / `<mutex>` / `<future>` 等头**：取 wasip1 那一支本来就不带，删头只会让报错更难懂。
- **不做「`initial = maximum` 预分配满内存」**：`memory.grow` 实测不贵（161 MiB 全程 14 ms），而预承诺 256 MiB 会拖慢每一次运行并顶破 `--max-memory` 的上限语义。
- **不开多线程 / 不为 `std::thread` 改站点的跨域设置**：站点本来就在 COOP+COEP 的跨域隔离态，这条不需要「新增风险」来换零收益。
- **不照抄那段 `supportsWasmExceptions` 探测代码**：它恒为 true（探测物不含任何异常指令）。
- **不把 `--no-check-features` 当空指针陷入开关**：它是关掉链接期特性兼容性校验，与第 0 页无关。
- **不把外部给的 6.7× / 3–5 MB / +100~300 ms 当基线**：一律以 §18 与 §18.8 的复测数为准；本文只在「目标」列引用它们。
- **不改判定语义**：那是 `docs/评测判定规范.md` 的职权，本文只提出「换内核之后哪些条目需要重新量」（§3 阶段 3）。
