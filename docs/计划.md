# 计划（下一步要做的事）

**与 [`废案.md`](废案.md) 相对**：那份是「明确不做 / 已冻结」，这份是「还没做、打算做」。

每条只写五件事：要什么、现在有什么、差哪几步、哪些口径没定、怎么验。**做完一条就把这一条从这里删掉，结论按既有纪律写进 `HANDOFF.md`** —— 这里不留历史，别让它长成第二份交接文档。

2026-10-20 定下两条（用户口径原文）：

- 「提交题目」= **提交到 Codeforces**，不是「站内跑一遍用例记一次账」；
- 「写没写 / 通过没有」的标记，**文件树和页签两处都放**。

## 1. 开工前必须知道的现状（五条，都指到文件）

1. **站内没有「提交」这个概念**。判题只有「跑用例」一条路，verdict 是卡片上的瞬时结果：`runNotify.js` 只把它变成一条通知（CE 那条常驻，其余几秒后自己走），**不落库**，刷新即无。所以「通过了没有」这件事，今天在整个仓库里没有任何一处记着。
2. **题目身份 = `url`**（`services/vfs/problemImport.js` 文件头那段「身份判据是 url，不是文件名」）。重命名 / 移动 / 重新抓取都靠它认回同一个节点。
3. **状态不能塞进 `node.meta` 或 `node.config`**：
   - `meta` 是 `problemMeta.normalizeMeta()` 的**严格白名单**，且题目信息弹窗改难度时是**整体替换** —— 塞进去的字段会被静默抹掉；
   - `config` 在每次抓取时整体覆盖（唯一例外：本次一个样例都没带时保留旧 tests）—— 重抓一次就丢。
4. **扩展那条线的可复用件**（`~/Code/cph-companion`）：`cp-*` 消息对 + `capabilities` 能力协商（不按版本号比大小）、`src/fillCode.ts` 的「在 CF 页面上写 DOM、优先点页面自己的提交按钮」那一套、`src/cfIdentity.ts` 的登录态与 handle 判定、`waitForTabReload()` 的「表单 POST 回同 URL」确认法。提交这一趟与代填验证码是同一类活，照抄结构即可。
5. **两处 UI 都有现成的落点**：
   - 文件树：`FileTreeItem.vue` 已有 `tree-item__dot`（dirty 小圆点，7px），标记可以并排放在它旁边；
   - 页签：`EditorTabs.vue` 页签**左侧那颗图标位是三选一**（`isStaleTab` → dirty 圆点 → 文件图标），把状态插进这个让位顺序里就是**零新增宽度**。这一条很关键：页签宽度是内容撑出来的，组线段 / 芯片 / 拖拽落点全按实时 rect 量（`measureGroupLines`、`GROUP_LINE_R`），页签一加宽，那些几何全要跟着重算。

## 2. 事项一：文件树 / 页签上的「写没写、通过没有」

### 2.1 状态机

| 状态 | 判据 | 树 | 页签 | 落库 |
| --- | --- | --- | --- | --- |
| 未写 | 正文与 `templateForPath(path)` 逐字相同（或空） | 空心小环 | 不显示（留文件图标） | 是 |
| 已写 | 正文与模板不同，或该文件在 `dirtyIds` 里 | 实心灰点 | 灰点 | 是（dirty 态不落，落盘时补） |
| 提交中 | 请求已发出，未拿到 submissionId | — | 转圈 / 半透明 | 否（掉线即回「已写」） |
| 判题中 | 拿到 submissionId，verdict 还是 `TESTING` | 琥珀 | 琥珀 | 是 |
| 通过 | CF verdict = `OK` | 绿勾 / 绿点 | 绿点 | 是 |
| 未通过 | 其余 verdict（WA / TLE / MLE / RE / CE …） | 红点 | 红点 | 是（记住 verdict 码，tooltip 显示） |

「通过 / 未通过」的颜色沿用站内既有的 passed 绿 / failed 红（与评测卡片同一套语义），**不新造颜色语义**；真要加变量，`src/styles/base.css` 两套主题都给值。

### 2.2 「写没写」从哪来（唯一取数点）

- **判据只有一条**：正文 ≠ 该路径的模板。模板取 `services/fileTemplates.js` 的 `templateForPath()`，与抓题建文件时写进去的是同一份。
- **取数点只有一处**：`services/monaco/modelManager.js` 的 `save(fileId)`（正文唯一写盘口，`writeFile` 之后、清 dirty 之前）。那里已经握着路径与全文，比对一次是纯字符串操作，不额外读盘。
- **未落盘的编辑**：`dirtyIds` 里有它就按「已写」显示（不必等 800ms 自动保存），落盘后转成持久态。
- **存量回填**：这个功能上线前就已经写好的题，状态表里没有条目。启动后 idle 时按「节点带 `meta.url`」扫一遍、读正文比对一次落表；之后只走增量。别在树渲染路径里现读（几百道题会把 IDB 打满）。
- **边界**：用户把正文清回模板 → 退回「未写」（这是对的，别做成「写过就永久算写过」）；用户自己建的 `main.cpp` 没有 `meta.url`，不参与。
- **适用范围**：判据是「节点带 `meta.url`」，也就是**所有抓来的题**（扩展抓题 / 随机抽题 / 比赛导入），不限于抽题面板 —— 三条来源落的是同一个 `importProblem`，没必要只为其中一条做标记。

### 2.3 存哪

建议**独立一份**：`cp.problemStatus`（localStorage，`url → { w: 0|1, v: '', sid: '', at: 0 }`）。

- 键名登记进 `src/services/storageNames.js`（那里是持久化名的唯一出处，改名前必须配迁移）；
- **不随云同步**：云同步的边界是 `services/cloudProfile.js` 的 `SYNC_KEYS` 白名单（16 个键，见 `docs/云端同步服务.md` §6），VFS 本身也不同步；状态一多会把公开的配置体撑大，多设备之间还必然冲突；
- **孤儿条目**：文件被删后条目留着无害（同名题再导进来状态还在，反而合理），但要在启动 reconcile 时清掉「表里有、树里已无对应节点、且超过 N 天」的条目，别无限长。

### 2.4 界面

- **文件树**：`tree-item__row` 里、dirty 圆点之后放一枚 8px 标记；tooltip 现在由 `formatMetaTooltip(meta)` 拼（`problemMeta.js`），**在那份里追加一行状态**，别在组件里另拼一份。
- **页签**：插进左侧三选一的让位顺序（stale > dirty > 状态 > 图标）。若坚持「AC 也要看得见」而状态与 dirty 撞车，让 dirty 优先（正在写的内容比上次提交结论更急）；`title` 现在是 `getNodeById(item.id)?.path`，状态走第二行或 `aria-label`。
- 两处的判定数据同源：都读 `cp.problemStatus` + `dirtyIds`，**不许各算一份**。

### 2.5 文案

`src/i18n/messages/explorer.js` 新增 4–6 条（未写 / 已写 / 判题中 / 通过 / 未通过 / `{verdict}` 的插值），中英并排。组件里不许出现中文字面量。

### 2.6 验证

- 探针（`wasm-oj-browser-probe`）：手种一条带 `meta.url` 的节点 → 刷新看树与页签两处标记；改正文 → 状态翻面；把正文改回模板 → 翻回「未写」；删文件后条目仍在、树里不显示。
- **必测回归**：改棵 UI 之后要复测组线段（内收 8px）、芯片宽度、组内拖拽落点 —— 这三样都按 rect 现量，页签宽度一变就抖。
- `npm run verify` 基线不变（A/B/C/D/F 绿，E/G/H 既有红）。

## 3. 事项二：从站内提交到 Codeforces

### 3.1 目标与边界

用户在站内写好一题 → 点「提交」→ 由扩展在他**自己的 CF 登录态**下把代码填进 CF 的提交表单并点提交 → 站点等 verdict → 回写成本地状态（事项一的那两个状态位）。

**不做**：自己拼 POST 请求（要自己造 csrf 与表单，风险远大于收益）、自动重交、自动刷榜。

### 3.2 跨仓契约（新加，只能往后追加）

| 方向 | 消息 | 载荷 | 回执 |
| --- | --- | --- | --- |
| 页面 → 扩展 | `cp-submit` | `{ requestId, url, code, language }` | `cp-submit-result` |
| 扩展 → 页面 | `cp-submit-result` | `{ requestId, ok, reason, submissionId }` | — |
| 扩展 → 页面 | `cp-verdict` | `{ requestId?, url, submissionId, state: 'judging'\|'done', verdict, timeMs, memoryKb }` | — |

- `reason` 枚举沿用既有风格：`not-logged-in` / `handle-mismatch` / `page` / `no-tab` / `timeout` / `cooldown`。
- `capabilities` 加一项 `cf-submit`；站点侧**只有探到它才显示提交入口**（`useCompanionBridge.js` 里 `canFillCode` / `canContestBatch` 那套写法，老扩展下按钮根本不出现，等于功能不存在）。
- **这条契约一次改完两端并同时发版**：`bridge.ts` 文件头列的清单是跨仓契约，漏一边就是静默失效。

### 3.3 扩展侧（`~/Code/cph-companion`，建议 2.66.5 → 2.67.0）

1. `scripts/build/extension.ts`：新增 `SUBMIT_SITE_PATTERNS`（`https://codeforces.com/contest/*/submit*`、`/gym/*/submit*`、`/group/*/contest/*/submit*`、`/problemset/submit*`），并进 `host_permissions` 与 `content_scripts`（`document_idle`，与 `fillCode.js` 同一条理由）。**权限条数会变**，`SUBMISSION-AMO.md` 里那份数字要同步改。
2. `src/models/messaging.ts`：`MessageAction` **往后追加** `SubmitCode`（枚举是跨进程线上格式，插在中间会让旧标签页认错动作）。
3. `src/submitCode.ts`（新，照 `fillCode.ts` 的结构写）：只在提交页待命；填 `textarea[name="source"]`、按 **option 文本**（`GNU G++17` / `Python 3`）选 `select[name="programTypeId"]` —— **不硬编码 programTypeId 的数值**，CF 会改；csrf 由页面表单自带，点页面自己的提交按钮（找不到才 `form.submit()`）；**先回话、延迟 50ms 再点提交**（页面一跳转消息通道就断，这是 `SUBMIT_DELAY` 那条老经验）。
   - 开工前先对着一个真实提交页看一眼表单字段名，别照抄这里的猜测。
4. `src/background.ts`：
   - 动作编排：按 `url` 找到/打开题目页 → 取页面自带的 Submit 链接（题目页侧栏就有一个 `href` 带 `/submit` 的链接，**拿它比自己拼 URL 抗改版**；拿不到才按 `contestId + index` 拼）→ 打开新标签 → 调 `SubmitCode` → 等提交后的地址变成 `/submission/{id}`（复用 `waitForTabReload` 那套判据）→ 回 `cp-submit-result`；
   - verdict 轮询：`https://codeforces.com/api/user.status?handle={handle}&from=1&count=10`，`handle` 取 `cfIdentity.currentHandle()`，命中判据 = `problem.contestId` + `problem.index` 对得上**且** `creationTimeSeconds ≥ 提交时刻`；**每 2s 一次、上限 60s**（CF API 的限流就是 1 请求 / 2 秒，别并发），拿到非 `TESTING` 的 verdict 就广播 `cp-verdict` 收工。
   - `handle-mismatch` 那道闸门必须复用：登录的是别人时**一律不提交**，哪怕题目是本站发起的。
5. 发版：`package.json` 版本、`CAPABILITIES` 加 `cf-submit`、打 chrome / firefox / source 三个包、`web-ext lint` 0/0/0；站点侧 `extensionPackage.js` 的 `EXTENSION_VERSION` 与 `public/extension/*.zip` 同步换。

### 3.4 站点侧

1. `services/cfSubmit.js`（或并进 `useCompanionBridge.js` 一对新消息）：`submitToCodeforces({ url, code, language })`，先 `flush()` 把正文落盘，再发请求；`language` 由活跃文件后缀派生（`.cpp` → `GNU G++17`、`.py` → `Python 3`），认不出的后缀直接禁用入口。
2. 入口（建议两处，第二处是兜底）：
   - **评测面板页脚**一颗「提交到 Codeforces」，仅当 `activeNode.meta.oj === 'codeforces'` 且扩展有 `cf-submit` 时出现；
   - **页签右键菜单**一项，同上判据。
3. verdict 到达 → 写 `cp.problemStatus`（走事项一那个唯一入口，别另写一份）→ 通知（成功一条、失败一条，文案在 `messages/notifications.js`）。
4. 文案：`settings` / `notifications` 两个域补中英；**新界面文案要同步五处文档**（`guide.html` / `guide.en.html` / `help.js` / `docs/使用手册.md` / `index.html` noscript）—— 这一条按 §7 的老纪律，别漏。

### 3.5 还没定的口径（动工前问用户）

1. **gym / group 支不支持**：这两类要 apiKey，抓题那条线已经明确「靠扩展」；提交这边是同样放开，还是先只做 contest / problemset？
2. **语言由谁定**：按后缀自动（省事，但 `.cpp` 到底交 G++17 还是 G++20 要定一个默认）还是第一次弹一次让用户选、记住？
3. **同一份代码重复提交**要不要挡（防手滑 + 少踩 CF 的提交间隔）。
4. 提交历史要不要留多条（现在设计只留最后一次状态）。

### 3.6 风险

- **CF 的验证码 / 频率限制 / 账号风控**：真提交可能要求过验证码，那种情况只能报「page」并让用户手动交，别猜着重试。
- **verdict 轮询撞限流**：多开几个题同时等 verdict 就会互相拖慢，必须串行排队、共用一条 2s 的节拍。
- **改版**：提交页 DOM 变了就报 `page` 并降级为「手动去交」，绝不静默失败。

### 3.7 验证口径

- **无头探针能验的**：`cp-submit` / `cp-submit-result` / `cp-verdict` 三条消息的通路（用 stub 扩展往页面广播，不必真扩展）、按钮显隐（有 / 没有 `cf-submit` 能力两态）、状态机与落库、树与页签两处标记、失败分支（`not-logged-in` / `timeout`）。
- **只能人工验的**：真提交一次 —— 需要用户浏览器里的 CF 登录态，agent 代不了。核对 submissionId、verdict、耗时 / 内存是否与 CF 页面一致。
- 回归：`npm run verify` 基线不变。

## 4. 顺序建议

1. **阶段 1（纯站内）**：`cp.problemStatus` + 「写没写」判据 + 树 / 页签两处标记（先只做「未写 / 已写」两态，AC 位留空）。
2. **阶段 2（跨仓）**：扩展 `cf-submit` → 站点接 verdict → 补「通过 / 未通过」。
3. **阶段 3（可选打磨）**：点徽标跳 CF 提交页、提交历史、按状态过滤 / 排序。

## 5. 明确不做

- 站内自己记一份「提交」账（用户口径：提交只到 Codeforces）；
- 自动重交、自动刷榜、批量交一整场；
- 把状态塞进 `node.meta` / `node.config`（会被整体替换抹掉，理由见 §1.3）；
- 状态随云同步。
