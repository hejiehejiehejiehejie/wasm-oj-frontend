# 评测机判定规范（v1 草案）

- **版本**：2026-11-09
- **适用**：`src/services/engines/` 引擎注册表、`src/services/checkers.js` 比对器注册表、`src/services/outputDiff.js` 差异定位、`src/services/runner.js` 编排层，以及后续重写的评测核心
- **性质**：规范性文档，只定义“什么算 AC / WA / CE / TLE / MLE / RE / ERR”，不描述界面样式，也不替代各引擎自己的协议说明
- **状态**：口径已落地（比对器插件、三层优先级、差异定位、`-DONLINE_JUDGE`、引擎口径统一、§9 自动验收）；剩余差距见 §10

> 一句话：编译期只看 CE；运行期先看“谁先触发”（看门狗 TLE / 内存上限 MLE / 进程异常 RE）；正常退出后才比对输出（AC / WA）；基础设施故障一律 ERR，不算竞赛判定。

## 1. 判定结果集

| 判定码 | 含义 | 触发条件 | 是否计入 AC |
|---|---|---|---|
| `AC` | Accepted | 进程正常退出（exit 0）且输出比对通过 | 是 |
| `WA` | Wrong Answer | 进程正常退出（exit 0）但输出不匹配 | 是（未通过） |
| `CE` | Compilation Error | 编译/链接阶段非 0，或编译阶段超时 | 是（未通过） |
| `TLE` | Time Limit Exceeded | 运行段超过时限，或看门狗到点 kill | 是（未通过） |
| `MLE` | Memory Limit Exceeded | 有明确证据表明进程因内存上限而终止 | 是（未通过） |
| `RE` | Runtime Error | 非 0 退出、信号终止、WASM trap，且不归 TLE/MLE | 是（未通过） |
| `ERR` | Judge Error | 基础设施/引擎故障：服务不可达、协议错误、不支持的语言等 | 否 |
| （空） | 未判定 | 未运行、运行中、用户取消、结果过期 | 否 |

约定：

- `ERR` 不是竞赛判定。它表示“这次评测本身没跑成”，不得折算成 WA，也不得计入 AC。
- 卡片内部 `status` 仍为 `idle / running / passed / failed / error`；`verdict` 只在跑完后出现，取消则回到 `idle`。
- 本项目 v1 **没有** PE（Presentation Error）与 OLE（Output Limit Exceeded），不把这两种结果偷偷折成 WA 或 RE，见 §7。

## 2. 判定优先级

编译阶段与运行阶段分开判定：

1. 编译/链接失败或编译阶段超时 → `CE`。程序根本没有运行，后续一切不判。
2. 运行阶段按“第一个终止原因”判：
   - 看门狗到点 kill → `TLE`
   - 内存上限导致终止（有证据）→ `MLE`
   - 其他非 0 退出 / 信号 / trap → `RE`
   - exit 0 → 比对输出 → `AC` / `WA`
3. 同时发生或无法区分时：**`TLE` > `MLE` > `RE`**。看门狗是外层时间权威，已经到点就不再追究内存。
4. 基础设施错误 → `ERR`，不进入上面的优先级链。

依据：DOMjudge 的判定顺序是 TLE 在 RE 之前；Isolate 的 meta 只记录“第一个发生的事件”（`TO` / `SG` / `RE`），MLE 由上层根据 `cg-oom-killed` 再映射。各系统并不存在一份统一的全局优先级表，本规范取“编译独立 + 运行期先发生者优先 + 歧义时时间优先”。

### 2.1 边界情形

| 情形 | 判定 | 说明 |
|---|---|---|
| 编译超时（当前 60 s） | `CE` | 编译阶段失败，与 DOMjudge/AtCoder 的编译错误同属“未产出可执行文件” |
| 死循环且持续分配内存 | 看门狗先到 → `TLE`；OOM 先到 → `MLE` | 无法区分时按 `TLE` |
| `abort()` / 空 `assert`（退出码 134） | `RE` | 134 本身不是内存证据；只有分配真的失败过才判 `MLE`（§5.2） |
| 栈溢出 | `RE` | AtCoder 明确把 stack overflow 列入 RE；Isolate 报 SIGSEGV。不能因为“和内存有关”就判 MLE |
| 除零（SIGFPE / 136） | `RE` | WASM 下同属 trap；没有分配失败证据 → `RE` |
| 编译期就能确定的除零（`a / 0`） | 按实际输出判 `AC` / `WA`，卡片另加一行提示 | `-O2` 把它折成常量，产物里**没有除法指令**，运行期无从检测；而 `-O0` 的平台会真发 `idiv`、收 SIGFPE 判 `RE`。**不据此判死**：这条诊断对走不到的分支（`if (c) x = 10 / 0;`）同样会报，判死会误杀在别的 OJ 上正常的程序。见 §6 与 `HANDOFF.md` §20.7 |
| 空指针 / 越界（SIGSEGV / 139，WASM OOB trap） | `RE` | 越界不等于分配失败；`sbrk` 失败次数为 0 → `RE` |
| 非 0 退出但输出正确 | `RE` | CF 规则要求 return code 0；DOMjudge/Isolate/AtCoder/USACO 同 |
| `malloc` 返回 NULL 后程序自行降级并 exit 0 | 按输出判 `AC` / `WA` | 上限被“顶到”但程序没被杀，不算 MLE；DOMjudge/Isolate 同样不杀 |
| exit 0 但 stderr 有内容 | 按 stdout 判 `AC` / `WA` | stderr 只是诊断，CF 允许；四个引擎已统一为忽略 |
| 期望为空、输出也为空 | `AC` | 归一化后都是 0 行 |
| 期望非空、输出为空 | `WA` | |
| 输出超长 | v1 不判 `OLE` | 受内存上限约束；输出捕获没有独立上限，见 §10 |
| 交互题 / SPJ / PE | 不支持 | v1 只有文本行比对 |

## 3. 状态机（单个用例）

```text
idle ──运行开始──> running ──┬─> passed   (AC)
                              ├─> failed   (WA)
                              └─> error    (CE / TLE / MLE / RE / ERR)
running ──用户取消──> idle（不产生 verdict）
```

- `stale` 是界面标记，不是判定：代码或输入改动后，旧结论标为“结果待重测”，保留 verdict 但不计入当前 AC 计数。
- 同一批用例并发上限为 2；单个用例的判定互不影响，不使用“第一个失败点”覆盖其它用例的结论。

## 4. 时间口径

### 4.1 行业口径

| 系统 | 口径 |
|---|---|
| DOMjudge | 以 CPU 时间为主，另设更宽松的墙钟；soft = 题目时限 × 语言系数，hard = soft + `max(1 s, 10%)`；soft 超过即 TLE |
| Isolate | `--time` 是 CPU 时间（“Time in which the OS assigns the processor to other tasks is not counted”）；`--wall-time` 是墙钟；`--extra-time` 只用于超限后继续等一小段以报告真实耗时 |
| AtCoder | 规则原文：“Execution time is measured as the maximum of real time and CPU time.” |
| Codeforces | 公开规则只要求“fit into the given time limit”，未公开 CPU/墙钟细则；TLE 会重跑确认 |
| USACO | C/C++ 通常每测试点 2 s |

### 4.2 本项目口径

- `timeLimitMs` **只覆盖运行段**，不含编译。编译另有 60 s 超时，超时判 `CE`。
- v1 只能测墙钟（WASM/JS 里拿不到 CPU 时间）。因此：
  - 判定阈值是 `T = timeLimitMs`；
  - 程序结束时刻晚于 `T` → `TLE`；
  - 看门狗到点仍未结束 → `TLE`。
- 看门狗在 `T + max(100 ms, 5% × T)` 处才 kill，判定用**程序结束时刻**（而非消息处理时刻）与 `T` 比较。宽限只规避事件循环卡顿造成的误杀，不改变 `TLE` 阈值。**已落地（2026-10-25）**：看门狗按上述宽限 kill；`runCase` 用宿主补丁记的 `_start` 起止墙钟（`runMs`）与 `T` 比较，超了即 `TLE`（即使程序自己已退出）。
- 已知限制：墙钟包含浏览器调度、GC 和其它标签页的影响，机器繁忙时可能误判 TLE。AtCoder 把 real time 计入，本身就接受这种偏保守的口径；CF 用重跑降低误判。v1 不做重跑，记录为已知偏差。
- 卡片上的 `durationMs` 必须表示**运行段墙钟**。仅能提供 HTTP 往返耗时的引擎（Judge0 / Piston）不得把该值当作 TLE 依据，见 §9。
- **同一份产物的第一遍不算数**（2026-10-26 落地）：`wasm` 引擎的 C++ 线复用同一个 `WebAssembly.Module`，而这份 Module 的第一遍执行跑在 V8 的 Liftoff 基线代码上，比稳态慢 25–40%（实测 300M 次循环 602.9 → 427.6 ms）—— 偏差全落在第一条用例上，足以造成误判（实测时限 175 ms：首条 TLE、后两条 163 / 161.5 ms 通过）。因此 `cold`（Module 刚编出来）且 `exit 0` 的那一遍**整遍丢弃**（耗时与输出都不要），由第二遍给出结论；第二遍若仍 `cold` 则退回第一遍，最多两遍。代价是「改完代码后的第一次运行」首条墙钟多一遍程序运行，上界 `T + max(100 ms, 5% × T)`。Python 不适用 —— 它每条用例本来就是全新实例。

## 5. 内存口径与栈空间

### 5.1 行业口径

| 系统 | 口径 |
|---|---|
| DOMjudge | 用 cgroup 的 `memory.peak` 统计“实际分配的总内存”，**包含 shell、解释器与栈**；`memory_limit` 以 kB 计；没有内存的 soft/hard 两档；超限通常表现为 abort，最终归入 RUN-ERROR |
| Isolate | `--mem` 限制单进程地址空间（kB）；`--cg-mem` 限制整个 cgroup 的总内存；`max-rss` 只算进程 RSS，漏掉子进程、共享页与 page cache，**不能单独用来判 MLE**；OOM 被杀报 `SG` + `cg-oom-killed`，由上层映射成 MLE |
| Codeforces / AtCoder | 有独立 MLE；常见 256 MiB / 1024 MiB |
| USACO | 约 256 MiB，反馈里 `!` 同时表示 RE 与 MLE |

关键结论：**MLE 的判据必须是“内存上限直接导致终止”**，而不是“内存看起来很大”。RSS 不是可靠口径，整组/整实例的总内存才是。

### 5.2 本项目口径（WASM）

- `memoryLimitBytes` = **WASM 线性内存总上限**，按 64 KiB 页向上取整，通过链接期 `--max-memory` 烙进产物。它同时包含栈、静态数据和堆，语义上更接近 DOMjudge 的“总内存”，而不是 RSS。
- MLE 证据（2026-10-25 起）：链接期塞入一段探针 —— 自定义 `sbrk` 顶掉 libc.a 里的那份，每次 `memory.grow` 失败记一笔，并导出 `__oj_sbrk_get()`；宿主补丁（`scripts/patch-wasi-clock.mjs`）在 trap 之后把失败次数、trap 原因、线性内存字节数与 `_start` 墙钟一起带回主线程。判据：
  - `memoryLimitBytes > 0` + 退出码 134 + `sbrkFailures > 0` → `MLE`；
  - 134 但失败次数为 0（空指针、运行期除零、`abort()`、栈溢出）→ `RE`；
  - 宿主补丁缺失（拿不到计数）时退回旧的「134 + 空 stderr」启发式 —— 它已知会误判，但不会把真正的 MLE 判成 RE。
- 探针语义与 wasi-libc 的 `sbrk` 一致：增量须为 64 KiB 页的整数倍且非负（否则 `abort`），成功返回旧页号 `<< 16`，失败返回 `(void*)-1`。唯一差异是不写 `errno`：clang 8 的 wasm 后端在这套 sysroot 上给 TLS 变量 `errno` 选不出指令，而 dlmalloc 只认 `(void*)-1` 返回值。探针只编译一次，`.o` 常驻内存。
- 已知边界：程序先遇到一次分配失败、随后因别的原因 `abort`，会被判 `MLE`（歧义时内存证据优先）；「分配了但从不读写」在 `-O2` 下仍可能被整段消除（§9 #6）。
- 已知边界（按内核分档，2026-10-25 拍板）：
  - **现役 8.0.1 档（异常关闭）**：`operator new` 失败时**静默返回空指针**，不抛 `bad_alloc`、也不 terminate；「`new` 到底、失败后不检查」的程序会一直跑下去，最终表现为 TLE 而不是 MLE。
  - **23.1.0 档（开异常）**：`operator new` 失败抛 `std::bad_alloc`。**未捕获** → terminate → abort（134），仍有 `sbrkFailures > 0` 这条证据 → `MLE`（与权威口径「内存上限直接导致终止」一致）；**被用户 `catch` 后正常退出** → 按程序自身结果判，不因「曾经分配失败」判 MLE（同 §9 #18 的 `malloc` 返回 NULL 后 AC）。实测见 §9 #22 / #23。
  - 两档共同的偏差：WASM 线性内存的 0 地址合法，**读**空指针不 trap（得到垃圾值）；写空指针在 `-O2` 下被折成 `unreachable`，实测判 `RE`（#7）。是否用 `-fsanitize=null` 兜底仍待拍板（`新内核规划.md` §5 第 5 项）；**当前实现不启用**，按「WASM 固有偏差」记录。
- 栈溢出仍判 `RE`，不因“栈也是内存”改判 MLE。

### 5.3 栈空间

行业值：Linux 默认 8 MiB，CF 显式给 256 MiB，AtCoder 没有公开的 C++ 栈参数。旧实现只给 1 MiB，深搜/递归题容易被无辜判 RE。

但不能直接把 CF 的 `256 MiB` 抄过来：WASM 的栈在线性内存内部，若 `--max-memory=256 MiB` 同时 `stack-size=256 MiB`，初始内存就会顶满上限，堆没有空间。规则：

```text
stack = min(64 MiB, max(8 MiB, memoryLimitBytes / 4), memoryLimitBytes / 2)
向下取整到 64 KiB 页
```

效果：64 MiB 上限 → 16 MiB 栈；128 MiB → 32 MiB；256 MiB 及以上 → 64 MiB。内存总上限不变，只是从堆预算里划走栈空间。

- 不采用“`--max-memory = 上限 + 栈`”的方案：那会让程序实际可用内存超过题目上限，偏离 DOMjudge/Isolate 的“总内存含栈”口径。
- 栈大小由内存上限推导，因此编译缓存键必须带一个 `STACK_POLICY_VERSION`，否则会复用旧 1 MiB 栈的产物。
- **已落地（2026-10-25）**：`runnoSandbox.stackSizeBytes()` 按上式算，链接期 `-z stack-size=` 生效；缓存键为 `(code, memoryLimitBytes, stackPolicy=1)`，其中任一项变化都重链接。256 MiB 上限下实测 11 × 16 MiB 堆分配后 `memory.grow` 失败（栈 64 MiB + 堆约 176 MiB ≈ 240 MiB，加静态数据贴近 256 MiB 上限）。

## 6. 编译参数基线

| 环境 | 编译器 | 标准 | 优化 | 宏 | 栈 |
|---|---|---|---|---|---|
| CF GNU G++20 | g++ 11.2.0 | `-std=c++20` | `-O2` | `-DONLINE_JUDGE` | `-Wl,--stack=268435456` |
| CF GNU G++23 | g++ 14.2 | `-std=c++23` | `-O2` | `-DONLINE_JUDGE` | 同上 |
| AtCoder C++20 | g++-12 | `-std=gnu++20` | `-O2` | `-DONLINE_JUDGE -DATCODER` | 未公开 |
| USACO | g++ 7.5.0 | `-std=c++11` 或 `c++17` | `-O2` | — | 未公开 |
| 本项目 WASM | clang 8 (WASI) | `-std=c++17` | `-O2` | `-DONLINE_JUDGE` | 16 / 32 / 64 MiB（按内存上限推导，见 §5.3） |
| 本项目桌面端 | 本机 clang++ / g++ | `-std=c++17` | `-O2` | `-DONLINE_JUDGE` | 宿主默认 |

规范性要求：

- **优化级别不得低于 `-O2`**。`-O0` 会让大量算法题的实测耗时失去参考意义，也与所有主流平台不一致。
- 警告开关**不参与判定**，只影响卡片上的提示。网页端原用 `-w`（全抑制），2026-10-26 换成 `-Wno-everything` 并在用户代码那次编译上单独放开 `-Wdivision-by-zero`（`-w` 是「全抑制」位，后面的 `-Wxxx` 压不动它）。后者唯一的产物是卡片上多一行「源码含除以零（编译期已确定），输出结果不可预期」，`AC` / `WA` 照旧按实际输出判（§2.1）。行业平台开 `-Wall -Wextra` 是为了给选手看警告，不是判定条件。
- 建议补 `-DONLINE_JUDGE`（可再加项目自己的宏），让用户代码里常见的 `#ifdef ONLINE_JUDGE` 分支生效。这是当前与 CF/AtCoder 最直接的一处差异。**已补（2026-10-25）**：网页端放在 `runnoSandbox.js` 的 `FRONTEND_ARGS`（属于语言选项，会写进 PCH 签名，因此 `PCH_CACHE_VERSION` 3 → 4），桌面端 `native.rs` 同一条 —— 两处是跨端契约，必须一起动。
- `-static` 在 WASM 里无意义，不追求；桌面端也不要求。
- C++ 标准：现役 8.0.1 档 `c++17`（clang 8 不支持 C++20）；**23.1.0 档已拍板 `c++20`**（2026-10-25，依据见 `新内核规划.md` §5 第 2 项）。接线时本节表格、§8 与桌面端 `native.rs` 必须一起改。

## 7. 输出比对

### 7.1 行业口径

- DOMjudge 默认 `compare` 是逐行 diff（`diff -a`），是否忽略行尾空白由题目 compare 配置决定；另可挂 `special_compare`。
- Codeforces 默认 checker 一般忽略行尾空白与多余空行；Polygon 的 checker 用退出码 0/1/2/3 表示 OK/WA/PE/FL。
- 主流平台都不把“行尾空格/末尾空行”算成 WA。

### 7.2 本项目口径（比对器注册表）

`src/services/checkers.js` 是「什么算答对」的唯一出处，五种方式按 id 注册：

| id | 语义 | 用途 |
|---|---|---|
| `lines`（内置默认） | `CRLF`/`CR` → `LF`；逐行去掉行尾空格与制表符；去掉末尾空行；行数与逐行内容都相同才算通过 | 项目原口径（原 `compare.js`），用户没改设置、题目也没指定时用它 |
| `tokens` | 按任意空白切成词元，词元序列相同即可（忽略行首、行内、换行差异） | CF / AtCoder 默认口径（`testlib.h` 的 `wcmp`）；排版自由、答案唯一 |
| `strict` | 仅抹平 `CRLF`/`CR` → `LF`，其余逐字节相同；行尾空格、末尾空行、换行位置都算数 | ASCII art、严格排版表格 |
| `float` | 词元序列相同，数字按 `|a-b| <= 1e-6 * max(1, |a|, |b|)` 比较（非数字词元按字符串） | 浮点题 |
| `unordered` | 行内容与行数相同，顺序不限（多重集相等） | 集合 / 多解输出 |

- `lines` 的语义是：**行尾空白不敏感，行首和行内空白敏感**；`1 2` 与 `1  2` 是 WA。与 DOMjudge 默认 diff 加“忽略行尾空白”的常见配置一致。
- `strict` 也先做 `\r\n` / `\r` → `\n`：Windows 与 Linux 的换行符差异不该让一份正确程序变成 PE，主流评测机同样先统一换行再严比（§7.1）。这一条是**所有比对方式的公共前处理**，`normalizeNewlines()` 一处实现。
- **三层优先级**（2026-11-09 起）：

  ```text
  题目 meta.checker  >  全局设置 cp.checker  >  内置默认 lines
  ```

  - 全局档位在设置页「评测 → 输出比对」，默认值就是 `lines`，与旧行为完全一致；用户主动改过之后才生效（`usePersistentRef('cp.checker', ...)`，随云同步走 `SYNC_KEYS`，属于偏好而不是事实）。
  - 题目覆盖仍写进 `meta.checker`（资源管理器右键「题目信息」→「输出比对」），选项是「跟随全局设置 / 五种方式」；选中「跟随全局」时该字段存空串。
  - `meta.checker` **允许存 `lines`**：全局档位可能是 `tokens`，此时题目必须能把它钉回逐行，否则「显式选择」和「没选」不可区分。空的含义只剩「不覆盖」。未知 id 一律当作不覆盖，不报错、不静默放宽。
  - 比对方式随结果落盘（`runner.js` 的 `CasePatch.checker`），所以跑完之后再改设置，不会改写已有结果的呈现口径。
- 只有运行结果为 `ok`（exit 0）时才比对输出；非 0 退出即使 stdout 正确也先判 RE。比对器只回答「两段输出是否等价」，不参与 TLE / MLE / RE。
- 不做 PE。行数相同但仅空白不同，按所选比对器的规则该 AC 就 AC，该 WA 就 WA，不产生第三种结果。

### 7.3 差异染色（`src/services/outputDiff.js`）

判定与定位是两条独立的线：`checkers.js` 回答「算不算对」，`outputDiff.js` 只回答「差在哪」，不参与判定，也不改变 verdict。界面上**没有单独的差异面板**（2026-11-09 晚撤掉），差异全部落在 ACTUAL / EXPECTED 两个框里，且只改字色。

- `diffOutput(actual, expected, checkerId)` → `{ got, want } | null`。`null` 表示按该口径没有差异。两份标记分别落在两侧原文的绝对偏移上：

  | kind | 落点 | 颜色 | 含义 |
  | --- | --- | --- | --- |
  | `replace` | ACTUAL | WA 红（`--fail`） | 这一段两边不一样 |
  | `extra` | ACTUAL | RE 黄（`--err`） | 实际输出多出来的 |
  | `missing` | EXPECTED | RE 黄（`--err`） | 期望有、实际没有的 |

  缺失一律落在**期望侧**：实际侧那个区间长度是 0，染不出来。这样任何一处差异都必然出现在某一边，不存在「判了 WA 但两个框都看不出哪错」。唯一的例外是「实际是期望的前缀」（`10` 对 `100`）—— 边界吸附把两侧都推到整词，成为一段 `replace`（见下面的吸附条目）。
- 有差异可指、**且这一框里真画出标记**时，ACTUAL 的正文回到常规字色（`.out.is-diffed`）—— 整框的 `--fail-soft` 淡红会把红 / 黄标记的对比吃掉（浅色主题里两者几乎同色）。判据是 `Boolean(actualSegments)` 而不是 `Boolean(diffMarks)`：纯 `missing`（实际侧没有标记）或差异全在截断区外时，ACTUAL 一个字都不染，此时**必须保留判定色兜底**，否则「判了 WA 的实际框」和 AC 长得一模一样。
- 对齐：**元素对元素，按位置配**（2026-11-09 定稿），不做 LCS、不跨位置找配对。
  - **行按行号、行内按词位**（`lines`）：第 i 行对第 i 行；同一行里第 k 个词元对第 k 个词元。期望 `1/2/3`、实际只有一行 `2` 时，标实际侧第 1 行 + 期望侧第 2、3 行（不是把那个 `2` 对到第 2 行）；`1 2 3` 对 `2 3` 时第 1、2 个词各算一处不一致、第 3 个词算「少了」，而不是拿公共后缀把 `2 3` 整段对上、只报「多了个 1」。代价：多插一行 / 一个词之后，后面的全部标成不一致（用户已确认接受）。
  - **全局词位**（`tokens` / `float`）：第 k 个词元对第 k 个词元，配不上的挂尾巴。旧实现用 LCS，少一个词时能把后面救回来，但它会悄悄改掉位置：`3 1 2` 对 `1 2 3` 只剩一句「3 换了 3」。`float` 的相等判定带容差，容差内不计差异。
  - `unordered` 按行多重集比；`strict` 走整串公共前后缀（线性）。
- 只有**已经配对的两个单位内部**才再掐一次公共前后缀，只标真正不同的那几个字符 —— 否则整行变色等于没标。`lines` 下词元序列完全相同、只差间距（`1  2` 与 `1 2`）时按**词间缝隙**比（第 k 个词前后的那道空白对第 k 道）：元素位置没动，逐道缝隙比能精确指出是哪一处多 / 缺了空格；对整行掐一次前后缀则会把头尾两处多余空格之间的正确内容整段吞进去（`1  2 3 4 5  6` 会一行红到尾）。
- **词元边界吸附**：某个词元与它配上的那一个不一致时（`100[8]00`、`[Imp]ossible`），把切点推到词元外沿 —— 数字和单词在算法题里是原子语义单位，标半个反而让人以为只错了那一位。吸附后整段超过 `INLINE_CHARS = 24` 就放弃吸附（构造题里 50 位的 01 串不该整条变色）。`strict` 不吸附：它承诺的就是「精确到字符」。
  - **只有两侧的差异段都是零宽时**才跳过吸附。这正是「实际是期望的前缀」这一类（`10` / `100`、`1.5` / `1.50001`）：单边短路会让吸附一步都走不动，实际侧一个字都不标、只在期望侧染个 `missing` 的 `0` —— 多一位标 replace、少一位实际框全白，同一个错误两侧不对称。现在两侧都吸附到整词，`10`/`100` 与 `100`/`10` 标出来完全对称。
- **纯空白的差异换成可见符号**：空格 `·`、制表 `⇥`、换行 `↵`（后面补回真换行，行结构不变）。空格染成红色还是空格，`strict` 下最常见的「多敲了一个空格 / 多了一个空行」没有这一层就完全看不见。替换范围只到「看得出边界」那一层（2026-11-09 深夜收紧）：
  - 整段没有可见字符（一道多余缝隙、一个空行、一整行空格）→ 全换；
  - 有可见字符时**只换首尾的空白** → 整行多出的 `10 20 30` 保持原样（整段本来已是黄字，词间的中点只是噪音），`10 ` 变成 `10·`（尾随空格才是指认对象）；
  - 期望侧 `quiet` 段**一个字都不换**：它靠悬停时的下划线出现，提前把空格换成 `·`、把换行换成 `↵` 就等于在静默态上把差异画出来了。
  - 代价：拖选标记段复制时，剪贴板里可能是符号而不是原字符；「复制输出」按钮走的仍是真值。
- **空行也占一行**：多 / 缺的是一个空行时（`[\r\n100800]` 与 `[100800]` 的多重集差），标记退到它后面那个换行上 —— 否则区间零宽，什么都画不出来。
  - 位置要从**抹掉行尾空白之前**的位置算：`"   \n"` 裁完是空行，但它的换行在下标 3 而不是 0，用行首加换行长度会标到第一个空格上去。
  - **前 `shared` 行里一侧是空行**时（`\n10 20` 对 `10 20`）要整行落标，不能走词元：空行切出来是空数组，按词配一个标记都不会落在那一侧 —— 真正的罪魁祸首（多出来的空行）毫无高亮，反而是下一行正确的 `10 20` 被标成多出。现在实际侧的空行标红（落在换行上，显示为 `↵`），期望侧那行按「少了」标黄，两侧同号。
- **偏移一律在原文上数**：`\r\n` 只在判定时抹平，标记必须落在框里那段原文上。`strict` 的比较只能发生在归一化文本上，它的偏移由 `toRawIndex` 换算回原文。
- 上限：`MAX_CHARS = 100_000`（超出不给标记）、`MAX_MARKS = 120`（**差异处数**，不是段数）。按编号截而不是按数组长度截：`extra` 只进实际侧、`missing` 只进期望侧，两侧下标天然不对齐，各截 120 段会把某一处 `replace` 的另一半留在对侧 —— 悬停时只亮半边。按 `pair` 截住「同一处要么两侧都在、要么两侧都丢」，代价是最多 240 段。按位置配对是线性的，没有 LCS 那种 O(n·m) 的表。
- 截断态（超长样例只显示前缀 + 省略行）只保留落在前缀内的标记，越过前缀的丢掉 —— 前缀部分的偏移仍然成立，不能整段放弃。**一段都留不下时 `markSegments` 返回 `null`**（不是「一个含全文、`kind` 为 `null` 的段」）：调用方拿返回值当闸门，真值数组会让 EXPECTED 被拴进只读 `<pre>`、ACTUAL 又被撤掉判定色兜底，结果是「判了 WA、一个字没染、还长得像 AC」。
- **两侧同一处共用一个 `pair` 编号**：`replace` 在实际侧有一段、期望侧也有一段，同号。界面据此在鼠标停到任意一段时把对侧一起点亮（加一道下划线，仍不铺底色、不改字重 —— 后者会改变字符宽度，`<pre>` 里就是整行错位）。`extra` / `missing` 只有单侧，悬停时只有自己亮。
- 期望侧那份 `replace` 带 `quiet`：**平时不着色**，只在悬停时出现，且显示为 WA 红。理由是「EXPECTED 只标少了的内容」—— 每一处替换都把期望输出染一遍会让那一格变成红黄杂陈，反而看不出哪里真的缺东西。副作用是 WA 卡片上 EXPECTED 基本是只读视图（有标记才会切成 `<pre>`），点一下照旧能编辑。
- 不变量（`npm run verify:judge` 交叉验收）：**判定 WA ⇒ 至少一侧有标记；判定 AC ⇒ 两侧都没有**。两处前处理（换行 / 行尾空白 / 末尾空行）只要有一处写歪，这组就红。另外两条：**两侧共用同一 `pair` 的标记数必须等于 `replace` 的处数**（编号错开就会点亮错误的位置，而颜色看起来完全正常，单看颜色抓不到）；**同一侧的标记必须有序、不零宽、不越界、不互相压盖**（压盖了 `markSegments` 会跳段，标记就凭空少一段）。切片层另有一组渲染契约：**没有任何一段画得出来时必须回 `null`**、`quiet` 段不许换字形、有可见字符的标记段只换首尾空白 —— 这三条错了都不影响颜色，只影响「卡片看起来是不是 AC」。
- 只在 `status === 'failed'` 时计算。
- **总开关**（2026-11-09 加）：设置 › 评测 › 差异高亮（`cp.editorSettings.diffHighlights`，默认开）关掉之后，卡片的 `diffMarks` 在第一行就返回 `null` —— 连 `diffOutput` 都不进，两个框里一个字都不染，EXPECTED 也照旧是可编辑的 `<textarea>`（它切成只读视图的前提正是「期望侧有要标的东西」）。它关的只是**显示**：比对口径、verdict、结果落盘都不受影响。

## 8. 各引擎兑现矩阵

| 引擎 | 时限 | 内存上限 | 编译参数 | MLE 判据 | exit 0 + stderr | 耗时口径 |
|---|---|---|---|---|---|---|
| `wasm` | 看门狗 `T + max(100 ms, 5% × T)` kill；`runMs > T` 亦判 TLE | 链接期 `--max-memory` | clang 8，`c++17 -O2 -w -DONLINE_JUDGE` | 134 + `sbrkFailures > 0`（失败计数拿不到时退回 134 + stderr 空） | 忽略 stderr，按 stdout 判 | `_start` 起止墙钟 |
| `native` | Rust 轮询，到点 kill | **不兑现**（设置页已明示） | 本机编译器，`c++20 -O2 -w -DONLINE_JUDGE` | 无（内存超限可能表现为 RE/AC） | 忽略 stderr，按 stdout 判 | 运行段墙钟 |
| `judge0` | `cpu_time_limit` | `memory_limit` | 由服务端决定 | `memory ≥ limit` | 忽略 stderr，按 stdout 判 | 服务端 `time`（运行段 CPU 秒，缺失则空） |
| `piston` | `run_timeout` | **不兑现**（设置页已明示） | 由服务端决定 | 无 | 忽略 stderr，按 stdout 判 | `wall_time`，缺失退 `cpu_time` |
| `echo` | 无 | 无 | 无 | 无 | — | 不执行代码 |

- `durationMs` 一律表示**运行段**：远端引擎取服务端上报的运行时间，拿不到就是 `null`，绝不用 HTTP 往返顶替（规范 §4.2）。
- 「不兑现内存上限」由引擎注册表的 `enforcesMemoryLimit` 声明，设置页据此显示「该引擎不兑现内存上限，不会判 MLE。」——不把设置项静默吞掉。
- **23.1.0 档（双档并存，2026-10-25 拍板）**：编译行为是 `-std=c++20 -O2 -w -DONLINE_JUDGE` + `-fno-rtti` + `-target-feature +simd128` + **新标准 exnref** 那组 wasm 异常参数（`+multivalue` / `+reference-types` / `-mllvm -wasm-use-legacy-eh=false`），链接追加 `-lunwind`。两处用户可见差异：`-fno-rtti` 让 `dynamic_cast` / `typeid` 变成 CE；`+simd128` 单看要 Safari 16.4，而**整体下限由新标准 EH 决定**——Chrome 137+ / Firefox 131+ / Safari 18.4+（2026-10-25 按 MDN `try_table` / `catch_all_ref` 兼容表核对），`error.wasmUnsupported` 与四份用户文案都按这个写。接线后本节 `wasm` / `native` 两行按此同步。

引擎 outcome 到界面 verdict 的映射（`runner.js` 现行）：

| engine outcome | verdict | 卡片 status |
|---|---|---|
| `ok` + 输出匹配 | `AC` | `passed` |
| `ok` + 输出不匹配 | `WA` | `failed` |
| `compile-error` | `CE` | `error` |
| `timeout` | `TLE` | `error` |
| `mle` | `MLE` | `error` |
| `runtime-error` | `RE` | `error` |
| `unreachable` / `rejected` / 其它 | `ERR` | `error` |
| `cancelled` | 空 | `idle` |

信号与退出码口径（宿主为 Unix 时，shell 习惯用 `128 + 信号编号`）：

| 退出码 / 信号 | 含义 | 判定 |
|---|---|---|
| 0 | 正常退出 | 进入输出比对 |
| 134 / SIGABRT(6) | abort、断言失败，或分配失败后被程序显式终止 | 有 `sbrkFailures > 0` → `MLE`；否则 `RE` |
| 136 / SIGFPE(8) | 浮点异常、整数除零 | `RE` |
| 139 / SIGSEGV(11) | 段错误、空指针、栈溢出 | `RE` |
| 137 / SIGKILL(9) | 通常为 OOM 或被外部杀 | 有内存证据 → `MLE`；否则 `RE`（看门狗 kill 另判 `TLE`） |
| WASM OOB trap / worker 崩溃 | 越界、栈耗尽 | `RE` |

## 9. 验收矩阵

在 WASM 引擎、256 MiB 内存上限、1 s 时限下逐条验证；桌面端原生引擎单独标注差异。

**自动验收**：现役 8.0.1 档跑 `npm run verify:judge`（`scripts/verify-judge.mjs`，真实 dev server + 无头 Chrome，直接调 `runner.evaluateCase`）；23.1.0 档跑 `npm run wasm:core:verify`（`scripts/wasm-core/verify.mjs`，Node WASI 宿主 + 同一张表）。表里带 `knownActual` 的行只要求「实际值等于已知值」，出现别的值才算回归。2026-10-25 实测：**现役档 PASS 20 / KNOWN 0 / FAIL 0**（#20 跳过）；**23.1.0 档判定组 PASS 23 / FAIL 0**（#20 跳过）、能力组另 13 条全绿。

同一脚本还带三组不依赖编译的先验验收（2026-11-09 加）：**输出比对器** 17 条（五档 × 前处理边界）、**输出差异** 44 条（两侧各自被染色覆盖的原文片段 + 两侧配对编号的处数，含「应当没有差异」的用例、CRLF 回归、纯空白换成 `·` / `⇥` / `↵`、空行标记、纯空格行、词元吸附、前缀包含、元素按位置配），另各 1 条断言期望侧静默标记（`quiet`）数不超过配对数、同一侧标记有序 / 不越界 / 不重叠，还有 1 条**切片契约**（无可染 → `null`、`quiet` 段不换字形、整行标记保留原始空格、首尾空白照换），**比对器 ↔ 差异** 17 条交叉不变量（WA 必须至少一侧有标记、AC 必须两侧都没有）。合计 101 条，这些在判定矩阵之前跑，任一失败即 `exit 1`。三组全 PASS 是该轮判定矩阵可采信的前置条件。

## 10. 与当前实现的差距（按优先级）

**已落地（2026-10-25）**

1. ~~栈只有 1 MiB~~：按 §5.3 生效（16 / 32 / 64 MiB 按上限推导），编译缓存键带 `STACK_POLICY_VERSION = 1`。
2. ~~WASM trap / `abort()` 会被误判 MLE~~：MLE 的第一证据改为链接期 sbrk 探针记下的 `memory.grow` 失败次数（§5.2）；134 + 空 stderr 的启发式只在拿不到计数时兜底。验收表里空指针写入（§9 #7）、运行期除零（#8）、`abort()`（#9）已是 `RE`。
3. ~~未定义 `-DONLINE_JUDGE`~~：网页 `FRONTEND_ARGS` 与桌面 `native.rs` 已补，PCH 缓存版本 3 → 4。
4. ~~`judge0` / `piston` 在 exit 0 且 stderr 非空时判 `RE`~~：已统一为忽略 stderr、按 stdout 判。
5. ~~`judge0` / `piston` 的 `durationMs` 是 HTTP 往返耗时~~：改取服务端运行时间（judge0 `time`、piston `wall_time` / `cpu_time`），拿不到就是 `null`。
6. ~~`native` / `piston` 不兑现内存上限却仍接受设置~~：引擎注册表新增 `enforcesMemoryLimit`，设置页对不兑现的引擎明示「不会判 MLE」。
7. ~~看门狗到点即 kill，`durationMs` 不等于运行段~~：宽限到 `T + max(100 ms, 5% × T)`，TLE 由 `_start` 起止墙钟（`runMs`）与 `T` 比较；卡片上的 `durationMs` 就是这个 `runMs`。

**P2**

8. 无 `OLE`：输出捕获没有独立上限，超大输出可能先拖垮页面。若后续引入，建议优先级为 `TLE > OLE > MLE > RE > WA/AC`。
9. 无 `PE`、SPJ、交互题。
10. 墙钟无法排除调度抖动，TLE 可能偏保守；CF 用重跑确认，本项目未做。
11. 编译超时 60 s，较 USACO 的 30 s 更宽松；本地场景可接受，不必收紧。
12. `cap` 页对齐后实际上限略大于用户设置（最多多 64 KiB），展示时仍按用户设置值，避免“256 MiB 却显示 256.06 MiB”。
13. 异常关闭使 `new` 失败不抛异常（§5.2）：不检查返回值的程序会跑到 TLE 而不是 MLE。**23.1.0 档已开异常**，该偏差在 23 档消失（#22 / #23 实测）；8.0.1 回退档仍保留旧行为，待站点接线后按档说明。

## 11. 权威依据

以下为本规范抽取的原文或字段依据；版本会随官方手册更新，升级前应重新核对。

### DOMjudge（ICPC / CCPC 官方评测系统，Manual 9.0）

- 判定章节：<https://www.domjudge.org/docs/manual/9.0/judging.html>
- 配置参考：<https://www.domjudge.org/docs/manual/9.0/configuration-reference.html>
- 队伍手册（结果集）：<https://www.domjudge.org/docs/manual/9.0/team.html>
- 判题机安装（cgroups）：<https://www.domjudge.org/docs/manual/9.0/install-judgehost.html>

关键原文与事实：

- “Time limits … enforced primarily in CPU time, and secondly a more lax wall clock time limit.”
- 时间 soft = 题目时限 × 语言系数，hard = soft + `timelimit_overshoot`（默认 `max(1 s, 10%)`）。
- 内存用 cgroups 的 `memory.peak`，比传统 rlimit 更接近“实际分配”，**包含栈与运行时**；没有内存 soft/hard 两档。
- 现行 `determineVerdict()` 顺序：compare 异常 → TLE → RE → OLE → AC/WA → NO-OUTPUT。
- 现行结果集没有独立 MLE；内存超限通常表现为 abort，最终归入 RUN-ERROR。`results_prio` 里残留的 `memory-limit` 键不代表现行判定分支。
- 退出码 `139/136/134` 是 shell 的 `128 + 信号` 写法，判题内部记录的是信号 11/8/6。

> 注意：DOMjudge 区分的是软/硬**时间**限制，不是软/硬内存限制。

### Isolate（IOI / CMS 官方沙箱）

- 仓库：<https://github.com/ioi/isolate>
- man page：<https://www.ucw.cz/isolate/isolate.1.html>

关键语义：

- `--time` 是 CPU 时间，OS 把处理器分给其它任务的时间不计入；`--wall-time` 是墙钟；`--extra-time` 只用于超限后继续等待以报告真实耗时。
- `--mem` 限制单进程地址空间（kB）；多进程时限/内存只有开 `--cg` 才有效。
- `--cg-mem` 限制整个 cgroup 的总内存；OOM 被杀时以 SIGSEGV 终止，并在 meta 中给出 `cg-oom-killed`。
- meta 字段：`status`（`RE` / `SG` / `TO` / `XX`）、`exitcode`、`exitsig`、`killed`、`time`、`time-wall`、`max-rss`、`cg-mem`、`cg-oom-killed`、`message`。
- **没有 MLE 状态**；MLE 由上层根据 OOM 证据映射。
- `max-rss` 只统计进程 RSS，漏掉子进程、共享页与 page cache，不能单独作为 MLE 判据。

### AtCoder

- 语言环境表：<https://img.atcoder.jp/file/language-update/language-list.html>
- 规则（时间口径）：<https://atcoder.jp/contests/dp/rules>
- 术语表（状态）：<https://atcoder.jp/contests/adt_all_20260611_1/glossary>

关键事实：

- C++20 编译命令包含 `-std=gnu++20 -O2 -DONLINE_JUDGE -DATCODER -Wall -Wextra -mtune=native -march=native` 及若干 constexpr 上限参数。
- 规则原文：“Execution time is measured as the maximum of real time and CPU time.”
- 常见限制 2 s / 1024 MiB，也有 256 MiB 的题目。
- RE 的官方举例包含 stack overflow、division by zero。
- 语言表只对 Java 给出 `-Xss`，C++ 没有公开的栈参数。

### Codeforces / Polygon

- Codeforces 命令行：<https://codeforces.com/topic/121739/en16>
- 比赛规则：<https://codeforces.com/blog/entry/4088>
- Polygon API：<https://codeforces.github.io/polygon-misc/API>
- Checker 教程：<https://codeforces.com/blog/entry/44571>

关键事实：

- GNU G++20（11.2.0）命令：`g++ -Wall -Wextra -Wconversion -static -DONLINE_JUDGE -Wl,--stack=268435456 -O2 -std=c++20`。
- 栈 268 435 456 B = 256 MiB；这是 Codeforces 显式给的，不是 AtCoder。
- 规则要求测试点通过需同时满足：return code 0、时间与内存均在限制内、答案正确。
- TLE 会重跑确认；状态含 MLE / TLE / RE / WA / Idleness limit exceeded / Denial of judgement。
- Polygon：`timeLimit` 250–15000 ms 且必须被 50 整除；`memoryLimit` 4–1024 MB；checker 退出码 0/1/2/3 对应 OK/WA/PE/FL。

### USACO

- 比赛说明：<https://usaco.org/index.php?page=instructions>

关键事实：

- g++ 7.5.0，`-O2 -lm`，`-std=c++11` 或 `c++17`。
- C/C++ 通常每测试点 2 s，Java/Python 4 s；内存约 256 MB；编译不超过 30 s。
- 反馈符号：`X`=WA、`T`=TLE、`!`=RE 或 MLE、`E`=空输出、`M`=缺输出；CE 显示编译器信息。
